## 1. 実証の範囲

### 含む
1. 顧問先がスキャンした画像を、顧問先専用のアップロードURLから提出
2. サーバーで自動読み取り → 構造化データとして保存 → 「確認待ち」に登録
3. 全画像の読み取りが完了したら、未確認CSVと元画像を税理士のGoogle Driveへ自動保存
4. 税理士が既存画面で案件を開き、元画像と照合・修正・途中保存
5. 必要な訂正だけを教訓として保存し、次回以降の読み取りに適用
6. 確定すると、確定版からCSVを作りDriveへ自動保存
7. Google Drive デスクトップで税理士PCに同期されることを実機で確認

### 含まない(後続)
メール受付、顧問先のセルフ登録、案内PDFの自動生成、LINE受付、書類種別の自動判定、エージェント連携、JDLの画面操作、スタッフ個別のログイン

### 前提
- 協力顧問先1社、スキャナー1種類、領収書・レシートのみ(既存の帳簿・Excel機能は維持)
- 紙原本は実証中保管する。法定保存(電子帳簿保存法)に対応済みとは扱わない
- 未確認データを本番の会計へ自動投入しない
- 受付形式は **JPEG / PNG のみ**。実機がPDFしか出せない場合は、ページ数上限とページごとの照合を含む対応案を別途提示する

## 2. 構成

```
顧問先のブラウザ(アップロード画面)
  └ 画像を1枚ずつ縮小し、元画像とOCR用画像を1ファイルずつ送信
Cloudflare Worker
  ├ API(認証・案件・アップロード受付・教訓)
  ├ Queues の処理側(画像ごとの読み取り)
  └ Drive への保存
D1(データベース) / R2(画像の非公開保管) / Google Drive API
税理士のブラウザ(既存画面を拡張した確認画面)
```

- 画像の前処理(縮小)は**ブラウザで行う**。Worker には画像処理に使う canvas がないため
- Worker の1回あたりのメモリ上限は128MB。**画像はまとめて読み込まず、1ファイルずつ送信・保存・処理する**
- Workers の無料プランは1回あたりのCPU実行時間が10ミリ秒(AIの応答待ちは含まない)。画像のエンコード等で超える見込みのため、有料プランを前提とする(費用は確認が必要。切り替えは税理士の合意後)

## 3. データの持ち方

### 行データは4つの値を分けて保存する

| 値 | 中身 | 用途 |
|---|---|---|
| AI原値 (`ai_raw`) | AIが返した構造化出力そのもの。**検算・補正の前** | 監査、精度の計測 |
| 補正後の初期値 (`auto`) | 検算・補正(読み上げ結論との不一致の訂正など)を適用した値。人の編集前 | 確認画面の初期表示、教訓用の差分の基準 |
| 現在値 (`current`) | 人が編集した値 | 途中保存、再表示 |
| 確定値 | 確定時点の全行のスナップショット | 確定CSVの出力元 |

- 補正の内容は警告として行に残す(何をどう補正したか)
- 現行コードの `validateReceiptRow` は入力行を直接書き換え、`row.original` は補正後に作られている。移植時は補正を「新しい値を返す処理」に変え、AI原値を補正前に保存する
- 教訓用の差分は `auto` と `current` の差(人が直した部分だけ)

### テーブル(D1)

| テーブル | 主な項目 |
|---|---|
| clients | id, 表示名, 受付トークンのハッシュ, Driveの保存先フォルダID, 有効/無効 |
| batches(案件) | id, client_id, 受付ID(提出単位で一意), 提出の状態(受付中/提出完了), 予定画像数, 確認状態, 版番号(rev), 確定した版 |
| files(画像) | id, batch_id, 順番, 元画像とOCR用画像のR2キー, ハッシュ値, 処理状態, 現在の処理実行ID, 試行回数, エラー, 検出枚数, 実際の枚数, 枚数照合済み |
| ocr_runs(読み取りの実行) | id(処理実行ID), file_id, モデル, プロンプトの版, **適用した教訓の本文とID**, 出力途切れ/JSON修復の有無, 状態, 開始・終了日時 |
| items(行) | id, batch_id, file_id, run_id, 順番, ai_raw, auto, current, 警告, 確度, 確認マーク, 削除フラグ |
| batch_warnings | id, batch_id, file_id, 種類(出力途切れ/JSON修復/枚数不一致/読み取り失敗など), 内容, 解決済み |
| lessons | id, 範囲(顧問先/事務所共通), client_id, 本文, 有効/無効, 元にした行, 作成・更新日時 |
| exports | id, batch_id, 種類(未確認/確定), 対象の版, 行データのスナップショット, 状態 |
| export_files | id, export_id, ファイル名, **Driveの事前生成ファイルID**, 状態, 試行回数, エラー |

## 4. 状態

```
提出の状態:  受付中(画像を1枚ずつ受付) → 提出完了(予定枚数がそろった)
画像の状態:  受付済 → 処理待ち → 処理中 → 完了 / 失敗(手動で再実行)
確認状態:    確認待ち → 確認中(途中保存あり) → 確定済み → (確定取り消し → 確認中)
出力の状態:  未送信 → 送信中 → 送信済み / 失敗(手動で再送)
```

- 確認状態と出力の状態は別に持つ
- **未確認CSVは「提出完了」かつ「全画像の処理が完了」した時点でだけ作る**。途中の状態からは作らない

## 5. 規則

### 5.1 受付
- 顧問先ごとに128ビット以上のランダムな受付トークンを発行し、サーバーにはハッシュだけ保存する。トークンでできるのはその顧問先への提出のみ
- 送信前の確認画面に「〇〇様 専用」と表示する(別の顧問先URLへの誤提出を減らすため)
- **受付IDは提出の開始時に1回だけ作り、同じ提出の再送では同じIDを使う**。サーバーは同じ受付ID・同じ順番の画像を1件にまとめる
- 同じハッシュ値の画像が過去の案件にある場合は警告を出す(自動でまとめない)
- 上限: 1回の提出は画像20枚まで、1枚10MBまで、1日の読み取り回数の上限を設定

### 5.2 読み取り
- 1画像=1メッセージで Queues に入れる
- 読み取りを始めるたびに処理実行IDを発行し、画像の「現在の処理実行ID」に記録する
- 結果の保存は**条件付き更新**: 画像の現在の処理実行IDが自分のIDと一致し、かつその画像の行がまだ編集されておらず、案件が確定済みでない場合だけ保存する。遅れて戻った古い処理の結果は捨てる
- 出力途切れ・JSON修復は `batch_warnings` に残す(画面の一時表示だけで終わらせない)
- AIが出す読み取り値の「AI原値」は補正前に保存する

### 5.3 再処理と教訓
- 教訓は**次回以降の読み取りにだけ**適用する。確認中の案件の値は変えない
- 再処理は画像単位の明示操作。その画像の行が1件でも編集済み、または案件が確定済みなら再処理できない
- 教訓は生成後に画面で文面を編集し、範囲(この顧問先/事務所共通、既定は顧問先)を選んで保存する
- 読み取りの実行ごとに、適用した教訓の本文とIDを `ocr_runs` に保存する(後で教訓を編集しても、そのとき何を渡したか分かる)
- 既存の localStorage の教訓は、管理画面のボタンでサーバーへ**無効状態で**取り込み、人が確認して有効化する

### 5.4 確認と確定
- 確認画面では、元画像の全体表示と、画像ごとの「検出枚数／実際の枚数」の照合を行う(座標による部分拡大は後続)
- 枚数の一致は検出漏れの対策であり、項目の正しさは保証しない(見逃し1枚と二重検出1枚でも一致する)
- **初回の実資料では、日付・金額などの主要項目も全件照合する**。以降の確認範囲は、その結果を見て決める
- 途中保存は版番号(rev)で同時編集を検知し、食い違えば保存を止めて知らせる
- **確定の条件**: 全画像の処理成功、全画像の枚数照合済み、未解決の警告なし、保存済みの版と画面の版が一致
- 確定するたびに版のスナップショットを作り、確定CSVは版ごとに別ファイルで出力する(上書きしない)

### 5.5 Driveへの保存
- フォルダ: `顧問先/年月/案件ID/未確認/` と `確定/`。未確認のファイル名には先頭に `未確認_` を付ける(未確認CSVをJDLへ誤って取り込まないため)
- 二重保存の防止: **ファイルごとにDriveのファイルIDを事前生成してDBに保存し、再送時も同じIDで作成する**。同じIDのファイルが既にあれば作成済みとして扱う
- Driveへの保存成功と、税理士PCへの同期完了は別のものとして、実機で確認する
- 認証方式は税理士のアカウント種別で決める
  - Google Workspace: 共有ドライブ+サービスアカウント
  - 個人のGmail: 本人のOAuth認可(サービスアカウントは保存容量を持たないため不可)。外部向けOAuthアプリが「テスト」状態だと更新トークンが7日で失効するため、公開状態にする
- アカウント種別の確認待ちでも、保存処理の共通部分とテスト用アカウントでの検証は進める

### 5.6 保持と削除
- 元画像は、Drive転送直後には削除しない
- R2の一律期限削除は、**保持期限の合意(Q-0018)前には有効にしない**。有効にする場合も、確認待ち・転送失敗中の案件の画像は消さない

### 5.7 安全
- 共有パスワードは、模擬データでの開発中の暫定運用とする。**実資料の投入前に管理側のアクセス制限を入れる**(全スタッフの権限管理までは作らない)
- R2は非公開。画像は認証済みのAPI経由でのみ表示
- Gemini API は有料(課金を有効にした)状態で使う。無料枠は送った内容がGoogleの製品改善に使われるため。**実資料の投入前に確認する**

## 6. 実装の段階

工数はClaude Codeを使った作業日数の目安。外部の回答待ちは含まない。

| 段階 | 内容 | 工数 |
|---|---|---|
| 0 | 土台(D1・R2・Queuesの作成)、Driveへの書き込みの試作(テスト用アカウント) | 0.5〜1日 |
| 1 | 共通ロジックの切り出し(補正の非破壊化)、D1、案件の保存・一覧・途中保存・再表示・確定、同時編集の検知 | 2〜3日 |
| 2 | アップロード画面(1枚ずつ送信、受付ID維持、提出完了の管理)、R2保存、Queuesでの読み取り(処理実行IDによる条件付き保存、警告の保存) | 2〜3日 |
| 3 | 確認画面に元画像の全体表示と枚数照合、Driveへの自動保存(事前生成ID)、確定条件、転送の再送 | 1.5〜3日 |
| — | **ここまでで初回デモ(6〜10日)** | |
| 4 | 教訓のサーバー保存(編集・範囲・有効/無効・実行ごとの適用記録)、localStorageからの取り込み、座標による部分拡大(任意) | 1.5〜2.5日 |
| 5 | 実機での実証、主要項目の全件照合、計測 | 1〜2日 |
| — | **実証完成(合計 8.5〜14.5日)** | |

- 段階1は既存の読み取りの流れを変えず、ブラウザで読み取った結果を「案件として保存」できる形から始める
- 有料プランへの変更、税理士の実アカウント接続、本番デプロイは、設定・費用・対象を具体化してから確認する。それに依存しない開発は進める

1. 税理士のGoogleアカウントの種類、共有ドライブの利用可否、管理者の制限、保存先、PC同期を確認する端末(段階3の実環境接続)

4. 協力顧問先のスキャナー機種、JPEG/PNGで保存できるか、試験用画像5枚程度(段階2の検証)

### 仮置きして進める

- 確認・確定の担当者: 共有パスワードで入れる人(開発中のみ)
- Slack: 任意
- 受信用ドメイン(Q-0014): 実証では不要

### 本番前でよい

## 9. v0.3 からの主な変更

| 項目 | v0.3 | v0.4 |
|---|---|---|
| 入力 | スマホで1枚撮影が主経路 | スキャナー画像を専用URLから提出 |
| 処理 | ブラウザで読み取り | サーバーで非同期に読み取り |
| データ | ブラウザ内(React状態・localStorage) | D1・R2に保存。AI原値・補正後・現在値・確定値を分離 |
| 出力 | CSVダウンロード | 未確認と確定を分けてDriveへ自動保存 |
| 保持 | CSV書き出しから30日で削除 | 合意した保持期限まで保持。合意前は自動削除しない |
| 教訓 | 端末ごと、即保存 | サーバーで共有、範囲と有効/無効、編集してから保存 |
